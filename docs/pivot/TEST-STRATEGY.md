# RustChat Buzz Pivot Test Strategy

**Status:** Proposed

The pivot is successful only if RustChat can consume upstream Buzz updates without silent behavior changes and if enterprise services cannot widen access or bypass Buzz security.

## Test layers

### 1. Upstream-preservation suite

Run the unmodified Buzz test commands in the Kubedo fork:

- Rust formatting and Clippy
- unit tests for every workspace crate
- relay integration tests
- Nostr interoperability tests
- MCP and ACP tests
- workflow tests
- media tests
- desktop type checks, unit tests, build, and Playwright tests
- web type checks, build, and Playwright tests
- Flutter analysis and tests

A downstream patch may not disable, delete, skip, or weaken an upstream test without an accepted exception.

### 2. Fork-divergence tests

Automated checks must verify:

- every downstream patch is in the patch ledger
- no forbidden patch class exists
- active patch count remains below the configured threshold
- published upstream migrations were not modified
- event-kind registries match upstream except for accepted upstream extensions
- protocol fixtures generated by upstream and Kubedo builds remain compatible
- branding-only commits do not change protocol, auth, schema, or event files

### 3. Contract tests

For each contract in `CONTRACTS.md`:

- JSON Schema or equivalent machine-readable schema validation
- producer tests
- consumer tests
- unknown-field behavior
- required-field behavior
- version-negotiation behavior
- idempotency behavior
- timeout and retry behavior
- authorization failure behavior

Contract tests run against the exact pinned Buzz and RustChat version matrix.

### 4. Identity security tests

Required scenarios:

- valid Authorization Code + PKCE login
- invalid issuer, audience, nonce, signature, and expired token rejection
- stable mapping by OIDC subject rather than email
- Buzz-key possession proof
- duplicate binding rejection
- user-owned and managed custody policy enforcement
- account suspension propagation
- organization membership revocation
- group change propagation
- device replacement and key recovery
- key rotation with historical attribution preserved
- Keycloak outage and token-expiry behavior
- replay, confused-deputy, and cross-organization attacks

### 5. Authorization intersection tests

For every knowledge or enterprise action, test all combinations of:

- active/suspended Keycloak account
- active/revoked organization membership
- Buzz relay membership
- Buzz channel membership
- RustShare artifact permission
- human/agent actor

The expected rule is deny when any required layer denies.

### 6. RustShare tests

- permission-filtered retrieval
- evidence/citation presence
- no existence leakage for forbidden artifacts
- channel-to-space mapping
- deletion and permission-revocation propagation
- bounded excerpts and output size
- agent access no broader than owner/configured policy
- dependency failure returns typed errors without breaking chat

### 7. Client tests

Desktop, web, Android, and iOS require:

- RustChat branding and no unintended Buzz/Block product marks in user-facing surfaces
- required Apache-2.0 attribution
- correct bundle/package identifiers
- correct update and deep-link endpoints
- Keycloak login and logout
- secure key storage
- community join and invitation
- messaging, threads, DMs, files, reactions, search, agents, and workflows
- push and background behavior where supported
- network loss, reconnect, and relay failover
- account suspension while logged in
- device replacement and restore
- privacy and terms links

### 8. Distribution and operations tests

- clean Docker Compose install
- clean Helm install
- immutable image digest enforcement
- readiness and liveness behavior
- backup and restore with checksums
- upgrade from previous RustChat distribution release
- rollback to previous tested matrix
- multi-replica relay behavior where supported
- S3, PostgreSQL, Redis, and Keycloak dependency failure
- observability fields and secret redaction
- SBOM and provenance generation

## Mandatory upstream-sync gate

Every proposed Buzz pin update must run:

1. upstream tests on upstream commit
2. upstream tests on Kubedo fork commit
3. fork-divergence checks
4. RustChat contract tests
5. identity and authorization tests
6. desktop/web/mobile smoke tests
7. upgrade test from the currently released matrix
8. generated compatibility report

The pin may advance only when all mandatory tests pass or an explicit, time-limited exception is approved.

## Release matrix

### Internal preview

Must pass:

- upstream relay and client tests
- identity login/binding/suspension tests
- RustShare permission and evidence tests
- Compose install and restore smoke test
- desktop smoke suite
- Android smoke suite

### Public preview

Additionally:

- iOS smoke suite
- push/background tests
- full upgrade and rollback
- security test review
- two upstream-sync cycles
- no critical unresolved fork-divergence issue

### Enterprise pilot

Additionally:

- high availability tests
- recovery-time and recovery-point validation
- export and retention tests
- penetration/security review findings addressed
- 30 days of internal dogfood
- documented support and incident runbooks

## LLM-generated code policy

Code origin does not change the gate. For every LLM-generated change:

- the prompt ID is recorded in `PROMPT-LEDGER.md`
- generated assumptions are listed in the PR
- tests are written from the contract/specification, before and apart from the implementation, by a prompt that has not seen the implementation (LLM-ALIGNMENT rule A2)
- security-sensitive code receives human review plus a context-free reviewer agent per LLM-ALIGNMENT rule A1
- every claimed verification includes the exact command and raw output or a linked CI run (LLM-ALIGNMENT rule A4)
- no generated migration may edit a previously released migration
- no generated change may reduce test coverage or mark failures as expected merely to make CI green

The full alignment rules, including the prohibited-agent-behavior list and the failure-mode map, are normative in [`LLM-ALIGNMENT.md`](./LLM-ALIGNMENT.md).

## Failure policy

A failing architecture or compatibility test is treated as evidence of a design problem, not an obstacle to bypass. Skipping, deleting, or weakening the test requires the same approval as changing the protected architecture rule.
